= Security, Observability, and Production Best Practices

While Red Hat AI Inference provides a fast path to serving language models, transitioning from a localized test to a production-ready deployment requires a shift in how we manage the container. Exposing an unauthenticated endpoint poses a severe risk to compute resources and data privacy. Furthermore, a production node must be observable, resilient, and capable of operating in highly regulated network environments.

For a standalone RHEL deployment, API security, encryption, and operational best practices must be integrated directly into your deployment strategy.

=== 1. Enforcing Authentication

By default, health monitoring endpoints like `/health` and `/ping` do not require authentication, but you can secure inference endpoints (like `/v1/chat/completions`) using built-in API key features. To secure the standalone server, you must pass the API key requirement when launching the container.

*Example: Starting the server with API key authentication*

[source,bash]
----
$ podman run --rm -it --name rhaii-server \
  --device nvidia.com/gpu=all \
  --security-opt=label=disable \
  --userns=keep-id \
  --shm-size=4GB -p 8000:8000 \
  --env "HUGGING_FACE_HUB_TOKEN=$HF_TOKEN" \
  --env "HF_HUB_OFFLINE=0" \
  --env=VLLM_NO_USAGE_STATS=1 \
  -v $HOME/rhaiis-cache:/opt/app-root/src/.cache:Z \
  registry.redhat.io/rhaii/vllm-cuda-rhel9:3.4.1-1780356914 \
  --model RedHatAI/granite-3.1-8b-instruct \
  --max-model-len 16384 \
  --api-key my-secret-token <1>
----
<1> Add your own secret or generated api-token key with api-key argument. 

*Key Arguments Used:*

* *`--api-key`:* Enforces the requirement for clients to pass the specified key. *Note:* For production, do not hardcode this in scripts; inject it securely via the `VLLM_API_KEY` environment variable.

==== Verification and Error Handling

When testing your secure deployment, the server will return standard HTTP status codes to indicate authentication success or failure:

* *200 OK:* The request was successful, and the model output is returned.
* *401 Unauthorized:* The request failed because the `Authorization` header (and the API key) was completely missing.
* *403 Forbidden:* The request failed because the API key provided did not match the key configured on the server.

=== 2. Enforcing TLS Encryption

To secure the standalone server comprehensively, you must pass both the API key requirement and the SSL/TLS certificate locations when you launch the container. Before running the container, ensure your SSL certificates (e.g., `tls.crt` and `tls.key`) are stored in a local directory on your RHEL server so they can be mounted into the container.

*Example: Starting the server with native TLS encryption in Podman*

[source,bash]
----
$ podman run -d --name rhaii-server \
  --device nvidia.com/gpu=all \
  --security-opt=label=disable \
  --shm-size=4GB -p 8000:8000 \
  -v ./rhaii-cache:/opt/app-root/src/.cache:Z \
  -v ./certs:/etc/ssl/certs:Z \
  registry.redhat.io/rhaii/vllm-cuda-rhel9:3.4.1-1780356914 \
  --model RedHatAI/Llama-3.2-1B-Instruct-FP8 \
  --api-key "<your_api_key>" \
  --ssl-certfile /etc/ssl/certs/tls.crt \
  --ssl-keyfile /etc/ssl/certs/tls.key \
  --enable-ssl-refresh
----

* *`--ssl-certfile` & `--ssl-keyfile`:* Points the engine to the mounted certificate files to enable HTTPS in-transit encryption.
* *`--enable-ssl-refresh`:* An optional but recommended flag that allows the server to automatically refresh the SSL Context if the certificate files are updated on the host, preventing the need to restart the container when certificates rotate.

Once the secure container is running, clients must communicate over `https://` rather than `http://` and pass the API key in the HTTP `Authorization` header.

=== 3. Observability: Exposing Prometheus Metrics

When developers complain that inference is slow, Platform Engineers need hard data to identify the bottleneck. The RHAII platform automatically exposes Prometheus metrics tracking critical inference data, including time-to-first-token (TTFT), time-per-output-token (TPOT), and GPU KV cache utilization. 

This gives us the exact visibility required to guarantee our SLOs and prove to leadership that our GenAI applications are performant.

You can easily scrape or view these metrics by querying the server's `/metrics` endpoint:

[source,bash]
----
$ curl -s http://localhost:8000/metrics | grep vllm
----

This output integrates directly into your existing enterprise Grafana dashboards, allowing you to monitor GPU utilization and token throughput in real time without deploying additional third-party agents.

=== 4. Day-2 Operations: Moving to Systemd

Throughout this course, we have been running the container interactively using `podman run --rm -it`. While excellent for rapid validation, a production node must run the inference server as a resilient background process that automatically recovers from failures and survives system reboots.

Because we are using RHEL and Podman, we can instantly translate our successful configuration into a native `systemd` service using Podman's built-in tools.

*Example: Generating a Systemd Service*
Once your container (`rhaii-server`) is running exactly how you want it in the background (using the `-d` flag instead of `-it`), you can generate the service file:

[source,bash]
----
# Generate the systemd service file directly from the running container
$ podman generate systemd --new --name rhaii-server > /etc/systemd/system/container-rhaii-server.service

# Reload systemd and enable the service to start on boot
$ systemctl daemon-reload
$ systemctl enable --now container-rhaii-server.service
----

Your LLM is now a fully integrated, managed infrastructure component.


=== 5. Air-Gapped Deployments: The Modelcar Advantage

[NOTE]
.Production Deployments
Throughout these labs, we utilized a Hugging Face token to pull model weights directly from the public internet. However, you cannot run sensitive corporate data through a public API. In strict enterprise environments, internet-connected downloads are forbidden.

To solve the air-gapped compliance problem, RHAII packages language models into OCI-compliant model containers (known as *modelcars*). This means we can distribute massive LLM weights using the exact same internal container registry infrastructure (like Red Hat Quay or Artifactory) that we already trust for standard application images. 

Instead of configuring `--env "HUGGING_FACE_HUB_TOKEN..."`, your production `podman run` command simply points the `--model` argument directly to your internal, authenticated registry, ensuring your AI infrastructure remains entirely offline and strictly compliant with industry regulations.

[WARNING]
.Registry Storage Capacity Warning
While modelcars solve compliance and network constraints, they introduce a major storage consideration for our infrastructure teams. Unlike standard application containers that measure in megabytes, OCI model container images are massive. Depending on the model's parameter count and whether it uses quantization, a single modelcar can range from 10 GB to well over 100 GB. Pushing several of these to an internal registry (like Red Hat Quay) requires significant planned storage capacity. You must warn your storage and registry administrators in advance to provision enough disk space to handle these artifacts.


=== 6. Gathering Diagnostic Data

Even with careful sizing and tuning, we will inevitably encounter edge cases, unexpected container crashes, or underlying hardware bugs. In a production enterprise environment, our safety net is vendor support. However, opening a ticket simply stating "the engine crashed" will severely delay our resolution time.

To streamline troubleshooting, the vLLM engine includes a built-in diagnostic tool. The `vllm collect-env` command automatically queries the environment and outputs critical system details, Python dependencies, and exact hardware configurations (including CUDA driver versions, GPU topologies, and TPU details).

*Example: Running the diagnostic script*::
You use this command after the crash. It acts as a probe that you drop into the exact same environment the crashed container was using, taking a snapshot of the hardware and software dependencies to hand over to the support team.

[source,bash]
----
$ podman run --rm -it \
  --device nvidia.com/gpu=all \
  registry.redhat.io/rhaii/vllm-cuda-rhel9:3.4.1-1780356914 \
  vllm collect-env
----

*Why it matters:* Whenever a critical AI workload fails or hangs unexpectedly, run this command and attach the output bundle to your Red Hat Support ticket. Providing this exact hardware and dependency snapshot upfront allows Red Hat engineers to bypass basic triage and immediately begin root-cause analysis, significantly reducing our downtime.
